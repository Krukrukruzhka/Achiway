# Achiway

## Назначение проекта

Achiway — приложение для постановки личных целей, контроля их выполнения и визуализации результатов. Приложением будут пользоваться несколько человек.

Проект развивается постепенно: каждый шаг должен давать небольшой, законченный и понятный результат.

## Согласованный стек

- Бэкенд: Python + FastAPI.
- Фронтенд: React + TypeScript.
- База данных: PostgreSQL (локально PostgreSQL 17 через Podman Compose).
- Доступ к БД: SQLAlchemy 2 + psycopg 3; миграции: Alembic. Зависимости согласованы пользователем.

Аутентификация: локальный логин и пароль с Argon2id, серверные сессии в PostgreSQL и `HttpOnly` cookie. Способ production-развёртывания пока не выбран; не добавляй его заранее без необходимости для текущей задачи.

## Структура проекта

- `frontend/` — React + TypeScript; экраны регистрации, входа, профиля и каталога привычек.
- `backend-services/app/` — FastAPI, регистрация и сессии, подключение к БД, профиль текущего пользователя, CRUD привычек и пользовательские шаблоны привычек; точка входа `app.main:app`.
- `backend-services/requirements.txt` — зависимости бэкенда с зафиксированными версиями; Python 3.10+ (проверено на 3.13).
- `backend-libs/` — заготовка для общих библиотек, пока только пустой `__init__.py`.
- `db/migrations/` — миграции Alembic; конфигурация находится в корневом `alembic.ini`.
- `compose.yaml` — локальная PostgreSQL; порт `127.0.0.1:55432`, данные в именованном томе `postgres_data`.

## Базовый API

- `GET /ping` — `{"message": "pong"}`.
- `GET /hello` — `{"message": "Hello, world!"}`.
- `GET /health/live`, `GET /health/startup` — HTTP 200 и `{"status": "ok"}`, без обращения к БД.
- `GET /health/ready` — проверяет доступность БД и всех таблиц приложения: HTTP 200 либо 503, если БД или схема недоступны.

## Аутентификация и профили

- Логин и никнейм — одно поле `login`. Логины нормализуются в нижний регистр, пробелы по краям удаляются. Длина 1–64, латинские буквы, цифры, `_`, `-`, `.`; первый символ — буква или цифра.
- Уникальность логина обеспечена ограничением PostgreSQL. Проверка формата в БД запрещает хранить ненормализованный логин.
- Постоянный идентификатор пользователя — UUID `id`; он сохраняется при смене логина.
- Необязательные поля: `name` (1–100 символов после удаления пробелов по краям), `gender` (`male`, `female`, `other`), `age` (целое число 0–150). Отсутствующее значение хранится как `NULL`.
- Пользователи самостоятельно регистрируются по логину и паролю. Пароль должен содержать 12–128 символов и хранится только как Argon2id-хеш в отдельной таблице `password_credentials`.
- Серверная сессия действует 7 дней. В браузер передаётся случайный токен в `HttpOnly`, `SameSite=Lax` cookie `achiway_session`; в БД хранится только SHA-256-хеш токена. Для production обязательно установить `SESSION_COOKIE_SECURE=true` и использовать HTTPS.
- `POST /auth/register` — создаёт пользователя и сессию, HTTP 201; занятый логин — 409.
- `POST /auth/login` — создаёт новую сессию, HTTP 200; неверные данные — 401 с общей ошибкой без раскрытия существования логина.
- После 5 последовательных неверных паролей новые попытки входа в учётную запись блокируются на 15 минут и получают HTTP 429. Успешный вход сбрасывает счётчик.
- `POST /auth/logout` — отзывает текущую сессию и очищает cookie, HTTP 204.
- `GET /auth/me` и `GET /users/me` — профиль текущего пользователя; без действующей сессии — 401.
- `PATCH /users/me` — частичное изменение своего профиля, HTTP 200. Можно сменить логин. Неуказанные поля сохраняются; `null` очищает необязательное поле, но запрещён для `login`.
- `DELETE /users/me` — удаляет текущего пользователя, его сессии и связанные данные, HTTP 204.
- Старые профили, созданные до миграции `0003`, не получают пароль автоматически и не могут войти. Нельзя открывать публичный сценарий назначения пароля такому профилю без отдельного подтверждения личности.
- Невалидные значения и неизвестные поля тела запроса — 422. Недоступная БД — 503.
- Изменение и удаление блокируют строку до завершения транзакции. Схема создаётся только миграциями, не при старте приложения.

## Привычки

- `habits` — общий каталог привычек. Название обязательно и уникально без учёта регистра; описание и категория необязательны. Категория хранится нормализованной строкой в нижнем регистре.
- `GET /habits`, `GET /habits/{habit_id}`, `POST /habits`, `PATCH /habits/{habit_id}`, `DELETE /habits/{habit_id}` — CRUD общего каталога. Используемая привычка не удаляется: API возвращает 409.
- Все ручки каталога привычек требуют действующую сессию.
- `user_habits` — пользовательские шаблоны. Цель состоит из положительного числового значения, единицы измерения и периода `day`, `week` или `month`.
- Одновременно может существовать только один активный шаблон пары пользователь–привычка. `POST /users/me/habits` создаёт шаблон текущего пользователя; `DELETE /users/me/habits/{user_habit_id}` архивирует только его собственный шаблон и не удаляет историю.
- Цель активного шаблона не изменяется. Для новой цели шаблон архивируется и создаётся заново.
- `habit_progress_entries` хранит по одному итогу на шаблон и календарный период. В записи сохраняется снимок цели. API для записей прогресса пока отсутствует.
- Статус записи прогресса согласован с результатом ограничением БД: `done` при достижении цели, `tried` при положительном результате ниже цели, `skipped` при нулевом результате.
- Удаление пользователя каскадно удаляет его шаблоны и записи прогресса.

## Локальный запуск и проверка

Команды выполняются из корня проекта. `docker` — существующий алиас на Podman; Docker Engine/Desktop не запускать. Алиас загружается в интерактивной zsh.

1. Установить зависимости: `.venv/bin/python -m pip install -r backend-services/requirements.txt` (если окружения ещё нет, сначала `python3 -m venv .venv`).
2. Если `.env` ещё нет, скопировать `.env.example` в `.env`. Заменить обе заглушки пароля одним локальным паролем. В URL спецсимволы пароля нужно percent-encode; пароль из hex-символов кодирования не требует. `.env` не коммитится.
3. При остановленной VM выполнить `docker machine start`. Запустить БД: `docker compose up -d --wait db`.
4. Экспортировать настройки и применить миграции:

   ```sh
   set -a
   source .env
   set +a
   .venv/bin/alembic upgrade head
   ```

5. В том же терминале запустить API: `.venv/bin/python -m uvicorn app.main:app --app-dir backend-services --host 127.0.0.1 --port 8000`.
6. Запустить frontend на `http://127.0.0.1:5173` привычной для локального окружения командой. При работе на порту `5173` frontend обращается к FastAPI на том же hostname и порту `8000`, передавая session cookie. Backend разрешает credentialed CORS только для `http://127.0.0.1:5173` и `http://localhost:5173`.
7. OpenAPI UI: `http://127.0.0.1:8000/docs`; готовность: `curl -fsS http://127.0.0.1:8000/health/ready`.

Пример тела `POST /auth/register`: `{"login": "demo_user", "password": "replace-with-strong-password", "name": "Пример", "gender": "other", "age": 25}`. Для очистки имени: `PATCH /users/me` с телом `{"name": null}`.
Пример тела `POST /habits`: `{"name": "Чтение", "description": "Читать книги", "category": "Самообразование"}`.
Пример тела `POST /users/me/habits`: `{"habit_id": "00000000-0000-0000-0000-000000000000", "target_value": 30, "target_unit": "минут", "target_period": "day"}`.

Проверки: `.venv/bin/python -m pip check`, `.venv/bin/python -m compileall -q backend-services db/migrations`, `.venv/bin/alembic current`, `.venv/bin/alembic check` (последние две требуют экспортированного `DATABASE_URL` и запущенной БД). Тестов и настроенного линтера пока нет.

Для следующего изменения схемы: изменить модель, выполнить `.venv/bin/alembic revision --autogenerate -m "описание"`, проверить сгенерированную миграцию и применить её через `upgrade head`.
Для остановки БД без удаления данных: `docker compose stop db`. Не удалять том и не выполнять downgrade без согласования: первая обратная миграция удаляет таблицу профилей.

## Порядок работы

- Общайся с пользователем на русском языке. Начинай с результата и пиши кратко.
- Перед изменениями прочитай применимые `AGENTS.md` и связанный код. Более близкие к файлу инструкции имеют приоритет.
- Реализуй только текущий согласованный шаг. Не добавляй будущие функции, инфраструктуру и абстракции «на вырост».
- Вноси минимальное целостное изменение, сохраняй несвязанные изменения пользователя.
- Следуй сложившимся в проекте архитектуре, именованию, форматированию и инструментам.
- Задавай вопросы, когда ответ существенно влияет на результат и его нельзя обоснованно вывести из контекста. Для остальных решений обозначай разумные предположения и продолжай работу.
- Не добавляй и не обновляй production-зависимости без объяснения необходимости и подтверждения пользователя.
- Не создавай и не изменяй тесты без явного запроса пользователя. Существующие тесты можно запускать.
- Запрашивай подтверждение перед разрушительными, необратимыми, внешне видимыми или потенциально затратными действиями, если пользователь явно не запросил именно это действие.
- Фиксируй принятые проектные решения, реальные команды и соглашения в соответствующем `AGENTS.md`. Не записывай предполагаемые команды как уже работающие.

## Принципы реализации

- Выбирай простые решения, соответствующие текущему этапу. Не вводи дополнительные сервисы без обоснованной необходимости.
- На бэкенде проверяй входные данные и явно описывай контракты API средствами FastAPI.
- На фронтенде используй типы TypeScript для данных и контрактов API; избегай необоснованного `any`.
- При появлении схемы БД веди её изменения через миграции и учитывай сохранность существующих данных.
- Не смешивай расчёт прогресса с его отображением. Формулы и правила прогресса согласовывай в рамках соответствующей задачи.

## Несколько пользователей и данные

- Учитывай многопользовательскую работу при проектировании хранения целей и доступа к ним.
- Проверяй права доступа на бэкенде; фильтрация в интерфейсе не заменяет проверку прав.
- Не доверяй переданному клиентом идентификатору пользователя как доказательству его прав.
- Не добавляй реальные персональные данные в примеры, фикстуры и логи.
- Не сохраняй пароли, токены и другие секреты в репозитории. Передавай конфигурацию окружения извне; в примерах используй безопасные заглушки.
- При работе со сроками различай календарные даты и точные моменты времени. Для моментов времени используй UTC в хранении и учитывай часовой пояс пользователя при отображении.

## Проверка и завершение задачи

- После изменения кода запускай наиболее подходящие доступные проверки: существующие тесты, линтер, проверку типов или сборку.
- Для изменений только в документации проверяй содержание и форматирование; сборка приложения не требуется.
- Проверяй итоговые изменения на соответствие задаче, случайные секреты, лишние сгенерированные файлы и отладочный код.
- В итоговом сообщении указывай, что изменено, что проверено и что проверить не удалось.
- Пока проект не содержит кода и настроенных инструментов, не придумывай команды запуска или проверки.
