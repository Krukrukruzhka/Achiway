# Achiway

## Назначение проекта

Achiway — приложение для постановки личных целей, контроля их выполнения и визуализации результатов. Приложением будут пользоваться несколько человек.

Проект развивается постепенно: каждый шаг должен давать небольшой, законченный и понятный результат.

## Согласованный стек

- Бэкенд: Python + FastAPI.
- Фронтенд: React + TypeScript.
- База данных: PostgreSQL (локально PostgreSQL 17 через Podman Compose).
- Доступ к БД: SQLAlchemy 2 + psycopg 3; миграции: Alembic. Зависимости согласованы пользователем.

Аутентификация: локальный логин и пароль с Argon2id, серверные сессии в PostgreSQL и `HttpOnly` cookie. Способ production-развёртывания пока не выбран; не добавляй его заранее без необходимости для текущей задачи.

## Структура проекта

- `frontend/` — React + TypeScript; экраны регистрации, входа, профиля, каталога и личных привычек; текущие экземпляры на главной и завершённые в истории.
- `backend-services/app/` — FastAPI, регистрация и сессии, подключение к БД, профиль текущего пользователя, CRUD привычек, пользовательские шаблоны и экземпляры с автоматической сменой периодов; точка входа `app.main:app`.
- `backend-services/requirements.txt` — зависимости бэкенда с зафиксированными версиями; Python 3.10+ (проверено на 3.13).
- `backend-libs/` — заготовка для общих библиотек, пока только пустой `__init__.py`.
- `db/migrations/` — миграции Alembic; конфигурация находится в корневом `alembic.ini`.
- `compose.yaml` — локальная PostgreSQL; порт `127.0.0.1:55432`, данные в именованном томе `postgres_data`.

## Базовый API

- `GET /ping` — `{"message": "pong"}`.
- `GET /hello` — `{"message": "Hello, world!"}`.
- `GET /health/live`, `GET /health/startup` — HTTP 200 и `{"status": "ok"}`, без обращения к БД.
- `GET /health/ready` — проверяет доступность БД и всех таблиц приложения: HTTP 200 либо 503, если БД или схема недоступны.

## Аутентификация и профили

- Логин и никнейм — одно поле `login`. Логины нормализуются в нижний регистр, пробелы по краям удаляются. Длина 1–64, латинские буквы, цифры, `_`, `-`, `.`; первый символ — буква или цифра.
- Уникальность логина обеспечена ограничением PostgreSQL. Проверка формата в БД запрещает хранить ненормализованный логин.
- Постоянный идентификатор пользователя — UUID `id`; он сохраняется при смене логина.
- Необязательные поля: `name` (1–100 символов после удаления пробелов по краям), `gender` (`male`, `female`, `other`), `age` (целое число 0–150). Отсутствующее значение хранится как `NULL`.
- Пользователи самостоятельно регистрируются по логину и паролю. Пароль должен содержать 12–128 символов и хранится только как Argon2id-хеш в отдельной таблице `password_credentials`.
- Серверная сессия действует 7 дней. В браузер передаётся случайный токен в `HttpOnly`, `SameSite=Lax` cookie `achiway_session`; в БД хранится только SHA-256-хеш токена. Для production обязательно установить `SESSION_COOKIE_SECURE=true` и использовать HTTPS.
- `POST /auth/register` — создаёт пользователя и сессию, HTTP 201; занятый логин — 409.
- `POST /auth/login` — создаёт новую сессию, HTTP 200; неверные данные — 401 с общей ошибкой без раскрытия существования логина.
- После 5 последовательных неверных паролей новые попытки входа в учётную запись блокируются на 15 минут и получают HTTP 429. Успешный вход сбрасывает счётчик.
- `POST /auth/logout` — отзывает текущую сессию и очищает cookie, HTTP 204.
- `GET /auth/me` и `GET /users/me` — профиль текущего пользователя; без действующей сессии — 401.
- `PATCH /users/me` — частичное изменение своего профиля, HTTP 200. Можно сменить логин. Неуказанные поля сохраняются; `null` очищает необязательное поле, но запрещён для `login`.
- `DELETE /users/me` — удаляет текущего пользователя, его сессии и связанные данные, HTTP 204.
- Старые профили, созданные до миграции `0003`, не получают пароль автоматически и не могут войти. Нельзя открывать публичный сценарий назначения пароля такому профилю без отдельного подтверждения личности.
- Невалидные значения и неизвестные поля тела запроса — 422. Недоступная БД — 503.
- Изменение и удаление блокируют строку до завершения транзакции. Схема создаётся только миграциями, не при старте приложения.

## Привычки

- `habits` — общий каталог привычек. Название обязательно и уникально без учёта регистра; описание и категория необязательны. Категория хранится нормализованной строкой в нижнем регистре.
- `GET /habits`, `GET /habits/{habit_id}`, `POST /habits`, `PATCH /habits/{habit_id}`, `DELETE /habits/{habit_id}` — CRUD общего каталога. Используемая привычка не удаляется: API возвращает 409.
- Все ручки каталога привычек требуют действующую сессию.
- `user_habits` — пользовательские шаблоны с личной необязательной категорией. Категория нормализуется в нижний регистр (1–64 символа), не меняет общий каталог; `null` означает «без категории». При создании без поля `category` копируется категория привычки из каталога. Миграция `0005` переносит категории каталога в существующие шаблоны.
- Цель состоит из положительного числового значения (до 9 цифр в целой части и 3 после запятой), единицы измерения (1–32 символа) и периода `day`, `week` или `month`.
- Одновременно может существовать только один активный шаблон пары пользователь–привычка. `POST /users/me/habits` создаёт шаблон текущего пользователя; `DELETE /users/me/habits/{user_habit_id}` архивирует только его собственный шаблон и не удаляет историю.
- `GET /users/me/habits` возвращает только активные шаблоны текущего пользователя. В интерфейсе они называются «Мои привычки»; привычку из каталога можно добавить себе и настроить категорию, период, цель и единицу измерения.
- `PATCH /users/me/habits/{user_habit_id}` частично меняет свой активный шаблон. Неуказанные поля сохраняются, `null` разрешён только для категории. Изменение только категории сохраняет ID. При изменении значения, единицы или периода цели прежний шаблон архивируется и создаётся новый в одной транзакции; ответ содержит новый ID. История прогресса остаётся у прежнего шаблона. Повторное сохранение той же цели не создаёт новую версию. Чужой или архивный шаблон — 404.
- `habit_progress_entries` хранит экземпляры привычек со снимками названия, личной категории, значения цели, единицы измерения и периода. Снимки не меняются при редактировании каталога или шаблона. `period_start` и `period_end` — точные моменты времени (`timestamptz`), границы полуинтервала `[start, end)`, хранятся как моменты UTC и рассчитываются/отображаются по `Europe/Moscow`.
- Первый экземпляр создаётся в транзакции добавления привычки пользователем. День длится до того же московского времени следующего дня, неделя — через 7 дней. Месяц заканчивается в то же время того же числа следующего месяца; если числа нет, используется последний день месяца. Исходное число сохраняется: 31 января → 28/29 февраля → 31 марта.
- Статус текущего экземпляра — `active` («Активно») даже при достижении цели. В конце периода он автоматически меняется на `done` («Выполнено») при результате не ниже цели, `tried` («Частично») при положительном результате ниже цели либо `skipped` («Пропущено») при нуле. Допустимость статуса проверяется ограничением БД. Закрытые экземпляры доступны только для чтения.
- `UserHabit.schedule_anchor` сохраняет исходную дату расписания, `next_instance_at` — начало следующего ещё не созданного экземпляра. При изменении цели версия шаблона по-прежнему меняется, текущий экземпляр прежней версии дорабатывает свой период. Новая версия начинает действовать на его границе. При сохранении периода сохраняется исходная привязка расписания; при смене периода новая последовательность начинается с конца текущего экземпляра. Категория также применяется только к новым экземплярам.
- Архивирование шаблона останавливает создание следующих экземпляров, но уже открытый остаётся доступен до конца периода. Повторное добавление той же привычки до его окончания не создаёт параллельный экземпляр: новый шаблон ждёт текущую границу.
- Фоновая задача в lifespan FastAPI проверяет наступившие границы раз в секунду, без дополнительных сервисов и зависимостей. После недоступности БД повторяет попытку через 30 секунд. При простое приложения восстанавливает все прошедшие периоды с нулевым результатом. Чтение экземпляров и изменения шаблона/результата также синхронизируют периоды. Точные границы не зависят от задержки обработки. Строки шаблонов блокируются на время транзакции; фоновый обработчик использует `SKIP LOCKED`, уникальные ограничения защищают от повторного создания.
- `GET /users/me/habit-instances?state=active|history&offset=0&limit=50` — экземпляры только текущего пользователя; ответ `{items, has_more, server_time}`. `limit` от 1 до 100. Активные упорядочены по ближайшему завершению, история — от новых к старым.
- `PATCH /users/me/habit-instances/{instance_id}` с `{"result_value": "12.5"}` заменяет суммарный результат текущего периода. Допустимы 0–999999999.999, до трёх десятичных знаков. Снимки и статус передать нельзя. Чужая/отсутствующая запись — 404, закрытая — 409, невалидный результат и лишние поля — 422, без сессии — 401.
- Миграция `0006` переводит календарные даты существующих результатов в московские границы и сохраняет результаты/статусы. Название и категория старых записей заполняются последними известными значениями. Расписание существующих активных шаблонов привязано к их `created_at`; обработчик восстанавливает периоды с этой даты, не перекрывая ранее сохранённые результаты.
- Удаление пользователя каскадно удаляет его шаблоны и записи прогресса.

## Навигация фронтенда

- Основные вкладки по порядку: «Главная» (`/`), «Мои привычки» (`/my-habits`), «Каталог» (`/habits`). Аватар открывает выпадающее меню с именем, логином, переходами в профиль (`/profile`) и историю (`/history`), а также кнопкой выхода. Меню закрывается при выборе пункта, переходе на другую страницу, клике или переводе фокуса за его пределы и по Escape.
- После входа открывается главная с активными экземплярами: название, категория, границы периода по Москве, снимок цели, статус «Активно» и редактирование общего результата за период. История показывает закрытые экземпляры со статусами «Выполнено», «Частично», «Пропущено» без редактирования. Оба списка имеют страницы по 50 записей, состояния загрузки, ошибки с повтором и пустые состояния. Данные обновляются при переходе, возвращении фокуса, каждые 30 секунд и на границе видимого активного периода; несохранённый ввод сохраняется при фоновом обновлении в пределах того же экземпляра.
- Каталог содержит поиск с квадратной зелёной кнопкой «+» рядом, без эффекта liquid glass. Плюс — центрированная SVG-иконка. Кнопка открывает одну модальную форму с названием и необязательной категорией каталога. «Добавить в каталог» отправляет только `POST /habits`, закрывает окно и обновляет каталог. Личный шаблон не создаётся; цель и период задаются отдельно через «Добавить себе» в «Моих привычках». Ошибки создания показываются в окне, введённые поля сохраняются для повтора. Окно закрывается крестиком, отменой, по Escape или клику на фон; во время сохранения повторная отправка и закрытие блокируются. Фокус удерживается внутри окна, прокрутка фона отключена.
- Поле поиска в каталоге выделено насыщенным серым фоном, серой рамкой и более тёмными подсказкой и иконкой; при фокусе оттенки остаются серыми.
- Кнопки «Добавить себе» и «Настроить» в каталоге ведут в «Мои привычки» по адресу `/my-habits?habit=<habit_id>` и раскрывают настройки соответствующей привычки внутри карточки. Если активного шаблона ещё нет, сверху отображается карточка добавления с категорией из каталога и пустой целью; запись создаётся только после сохранения обязательных параметров цели. Отмена или уход со страницы не создают шаблон. Если шаблон уже есть, открывается его редактирование без создания дубликата. Передаётся ID привычки, сохраняющийся при смене версии шаблона. Прямое открытие адреса, обновление и история браузера сохраняют выбор привычки; несохранённые поля при перезагрузке сбрасываются. Если привычки нет в каталоге, показывается ошибка без открытия другой карточки. Модальное окно в каталоге используется только для создания новой привычки по кнопке «+».
- В «Моих привычках» каждая привычка отображается отдельной карточкой с рамкой. «Настроить шаблон» раскрывает внутри карточки компактную форму категории, периода, значения цели и единицы измерения. Одновременно раскрыта одна карточка; «Свернуть», отмена или Escape в форме закрывают настройки без сохранения. Во время сохранения переключение и сворачивание карточек блокируются; при ошибке форма остаётся открытой. После сохранения карточка сворачивается и обновляется с учётом нового ID версии шаблона, сохраняя место в списке. Сворачивание или сохранение убирает параметр `habit` из текущего адреса без добавления записи в историю браузера. Пустой список предлагает переход в каталог. Создание привычки по кнопке «+» в каталоге остаётся модальным.
- В форме создания и настройки привычки отключено браузерное автозаполнение (`autocomplete="off"`), чтобы история ввода не перекрывала поля при открытии окна.
- Поле «Цель» при добавлении и настройке личной привычки принимает только целые числа от 1 до 999999999 (`step="1"`, дополнительная проверка перед отправкой). Контракт API и схема БД остаются прежними; существующие дробные цели не округляются автоматически.
- Компонент `HabitIcon` и CSS-класс `habit-icon` показывают SVG-иконку категории: спорт, здоровье, самообразование (также обучение и саморазвитие), работа, финансы, досуг, питание, сон. Для остальных категорий и без категории `habit-icon-empty` показывает пустой прозрачный квадрат с пунктирной рамкой толщиной 2 px. В каталоге используется категория каталога, в «Моих привычках» — личная категория шаблона.
- При переходе между экранами привычек данные загружаются заново; незавершённая форма закрывается. Навигация поддерживает прямые адреса и историю браузера.
- При ширине до 1100 px основная навигация отображается нижней панелью в один ряд из трёх пунктов с отступом для содержимого и безопасной области устройства.

## Локальный запуск и проверка

Команды выполняются из корня проекта. `docker` — существующий алиас на Podman; Docker Engine/Desktop не запускать. Алиас загружается в интерактивной zsh.

1. Установить зависимости: `.venv/bin/python -m pip install -r backend-services/requirements.txt` (если окружения ещё нет, сначала `python3 -m venv .venv`).
2. Если `.env` ещё нет, скопировать `.env.example` в `.env`. Заменить обе заглушки пароля одним локальным паролем. В URL спецсимволы пароля нужно percent-encode; пароль из hex-символов кодирования не требует. `.env` не коммитится.
3. При остановленной VM выполнить `docker machine start`. Запустить БД: `docker compose up -d --wait db`.
4. Экспортировать настройки и применить миграции:

   ```sh
   set -a
   source .env
   set +a
   .venv/bin/alembic upgrade head
   ```

5. В том же терминале запустить API: `.venv/bin/python -m uvicorn app.main:app --app-dir backend-services --host 127.0.0.1 --port 8000`.
6. Для frontend использовать Node.js 22 (не ниже 22.12; основная версия указана в `.nvmrc`). Установить зависимости командой `npm --prefix frontend ci`, затем запустить `npm --prefix frontend run dev`. Vite открывает `http://127.0.0.1:5173`; если порт занят, завершает запуск с ошибкой, не выбирая другой порт. При работе на порту `5173` frontend обращается к FastAPI на том же hostname и порту `8000`, передавая session cookie. Backend разрешает credentialed CORS только для `http://127.0.0.1:5173` и `http://localhost:5173`.
7. OpenAPI UI: `http://127.0.0.1:8000/docs`; готовность: `curl -fsS http://127.0.0.1:8000/health/ready`.

Пример тела `POST /auth/register`: `{"login": "demo_user", "password": "replace-with-strong-password", "name": "Пример", "gender": "other", "age": 25}`. Для очистки имени: `PATCH /users/me` с телом `{"name": null}`.
Пример тела `POST /habits`: `{"name": "Чтение", "description": "Читать книги", "category": "Самообразование"}`.
Пример тела `POST /users/me/habits`: `{"habit_id": "00000000-0000-0000-0000-000000000000", "category": "Самообразование", "target_value": 30, "target_unit": "минут", "target_period": "day"}`.
Пример тела `PATCH /users/me/habits/{user_habit_id}`: `{"target_value": 150, "target_period": "week"}`. Для очистки личной категории: `{"category": null}`.

Проверки backend: `.venv/bin/python -m pip check`, `.venv/bin/python -m compileall -q backend-services db/migrations`, `.venv/bin/alembic current`, `.venv/bin/alembic check` (последние две требуют экспортированного `DATABASE_URL` и запущенной БД). Проверки frontend: `npm --prefix frontend run typecheck`; `npm --prefix frontend run build` повторно проверяет типы и собирает приложение в `frontend/dist/`. Файлов тестов и настроенного линтера приложения пока нет.

## CI

- `.github/workflows/ci.yml` запускает GitHub Actions при pull request в `main`, push в `main` и вручную через `workflow_dispatch`. Независимые задания выполняются на `ubuntu-24.04`, имеют таймаут 10 минут; новый запуск отменяет предыдущий CI той же ветки.
- Frontend: Node.js 22 из `.nvmrc`, `npm ci` и `npm run build` в `frontend/`. `package-lock.json` фиксирует дерево зависимостей; `frontend/.npmrc` указывает публичный `https://registry.npmjs.org/`, чтобы сборка не зависела от корпоративного registry на компьютере разработчика. Для импорта CSS подключены типы `vite/client`.
- Backend: Python 3.13, установка `backend-services/requirements.txt`, `pip check`, `compileall`, `alembic upgrade head` и `alembic check`. PostgreSQL 17 создаётся как одноразовый service-контейнер с отдельной БД `achiway_ci`; пароль в workflow используется только для этой временной БД и не является production-секретом.
- После миграций CI запускает API и проверяет `/health/ready`, `/health/live` и `/health/startup`; процесс останавливается при завершении шага, его журнал попадает в вывод задания.
- Workflow имеет только `contents: read`, checkout не сохраняет credentials; официальные Actions закреплены по SHA. Серверные ключи и production-БД в CI не используются. В GitHub Actions service-контейнер работает через Docker; локально сохраняется правило использования алиаса `docker` на Podman.
- Этот этап добавляет проверки исходного кода и миграций. Сборка production-образов, публикация в GHCR и ручной деплой на сервер добавляются следующим шагом.

## Миграции и остановка БД

Для следующего изменения схемы: изменить модель, выполнить `.venv/bin/alembic revision --autogenerate -m "описание"`, проверить сгенерированную миграцию и применить её через `upgrade head`.
Для остановки БД без удаления данных: `docker compose stop db`. Не удалять том и не выполнять downgrade без согласования: первая обратная миграция удаляет таблицу профилей.

## Порядок работы

- Общайся с пользователем на русском языке. Начинай с результата и пиши кратко.
- Перед изменениями прочитай применимые `AGENTS.md` и связанный код. Более близкие к файлу инструкции имеют приоритет.
- Реализуй только текущий согласованный шаг. Не добавляй будущие функции, инфраструктуру и абстракции «на вырост».
- Вноси минимальное целостное изменение, сохраняй несвязанные изменения пользователя.
- Следуй сложившимся в проекте архитектуре, именованию, форматированию и инструментам.
- Задавай вопросы, когда ответ существенно влияет на результат и его нельзя обоснованно вывести из контекста. Для остальных решений обозначай разумные предположения и продолжай работу.
- Не добавляй и не обновляй production-зависимости без объяснения необходимости и подтверждения пользователя.
- Не создавай и не изменяй тесты без явного запроса пользователя. Существующие тесты можно запускать.
- Запрашивай подтверждение перед разрушительными, необратимыми, внешне видимыми или потенциально затратными действиями, если пользователь явно не запросил именно это действие.
- Фиксируй принятые проектные решения, реальные команды и соглашения в соответствующем `AGENTS.md`. Не записывай предполагаемые команды как уже работающие.

## Принципы реализации

- Выбирай простые решения, соответствующие текущему этапу. Не вводи дополнительные сервисы без обоснованной необходимости.
- На бэкенде проверяй входные данные и явно описывай контракты API средствами FastAPI.
- На фронтенде используй типы TypeScript для данных и контрактов API; избегай необоснованного `any`.
- При появлении схемы БД веди её изменения через миграции и учитывай сохранность существующих данных.
- Не смешивай расчёт прогресса с его отображением. Формулы и правила прогресса согласовывай в рамках соответствующей задачи.
