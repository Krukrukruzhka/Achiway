# Achiway

## Назначение проекта

Achiway — приложение для постановки личных целей, контроля их выполнения и визуализации результатов. Приложением будут пользоваться несколько человек.

Проект развивается постепенно: каждый шаг должен давать небольшой, законченный и понятный результат.

## Согласованный стек

- Бэкенд: Python + FastAPI.
- Фронтенд: React + TypeScript.
- База данных: PostgreSQL.

Библиотеки для работы с БД, способ аутентификации и способ развёртывания пока не выбраны. Не считай их согласованными и не добавляй заранее без необходимости для текущей задачи.

## Структура проекта

- `frontend/` — React + TypeScript; пустая страница с названием Achiway в шапке.
- `backend-services/app/` — базовое приложение FastAPI, точка входа `app.main:app`.
- `backend-libs/` — заготовка для общих библиотек, пока только пустой `__init__.py`.
- `db/` — резерв для работы с БД; пока только `.gitkeep`, без схемы и логики.

## Базовый API

- `GET /ping` — `{"message": "pong"}`.
- `GET /hello` — `{"message": "Hello, world!"}`.
- `GET /health/live`, `GET /health/ready`, `GET /health/startup` — HTTP 200 и `{"status": "ok"}`.
- Пробы подтверждают доступность запущенного приложения. Внешних зависимостей пока нет; проверки БД не добавлены.

## Порядок работы

- Общайся с пользователем на русском языке. Начинай с результата и пиши кратко.
- Перед изменениями прочитай применимые `AGENTS.md` и связанный код. Более близкие к файлу инструкции имеют приоритет.
- Реализуй только текущий согласованный шаг. Не добавляй будущие функции, инфраструктуру и абстракции «на вырост».
- Вноси минимальное целостное изменение, сохраняй несвязанные изменения пользователя.
- Следуй сложившимся в проекте архитектуре, именованию, форматированию и инструментам.
- Задавай вопросы, когда ответ существенно влияет на результат и его нельзя обоснованно вывести из контекста. Для остальных решений обозначай разумные предположения и продолжай работу.
- Не добавляй и не обновляй production-зависимости без объяснения необходимости и подтверждения пользователя.
- Не создавай и не изменяй тесты без явного запроса пользователя. Существующие тесты можно запускать.
- Запрашивай подтверждение перед разрушительными, необратимыми, внешне видимыми или потенциально затратными действиями, если пользователь явно не запросил именно это действие.
- Фиксируй принятые проектные решения, реальные команды и соглашения в соответствующем `AGENTS.md`. Не записывай предполагаемые команды как уже работающие.

## Принципы реализации

- Выбирай простые решения, соответствующие текущему этапу. Не вводи дополнительные сервисы без обоснованной необходимости.
- На бэкенде проверяй входные данные и явно описывай контракты API средствами FastAPI.
- На фронтенде используй типы TypeScript для данных и контрактов API; избегай необоснованного `any`.
- При появлении схемы БД веди её изменения через миграции и учитывай сохранность существующих данных.
- Не смешивай расчёт прогресса с его отображением. Формулы и правила прогресса согласовывай в рамках соответствующей задачи.

## Несколько пользователей и данные

- Учитывай многопользовательскую работу при проектировании хранения целей и доступа к ним.
- Проверяй права доступа на бэкенде; фильтрация в интерфейсе не заменяет проверку прав.
- Не доверяй переданному клиентом идентификатору пользователя как доказательству его прав.
- Не добавляй реальные персональные данные в примеры, фикстуры и логи.
- Не сохраняй пароли, токены и другие секреты в репозитории. Передавай конфигурацию окружения извне; в примерах используй безопасные заглушки.
- При работе со сроками различай календарные даты и точные моменты времени. Для моментов времени используй UTC в хранении и учитывай часовой пояс пользователя при отображении.

## Проверка и завершение задачи

- После изменения кода запускай наиболее подходящие доступные проверки: существующие тесты, линтер, проверку типов или сборку.
- Для изменений только в документации проверяй содержание и форматирование; сборка приложения не требуется.
- Проверяй итоговые изменения на соответствие задаче, случайные секреты, лишние сгенерированные файлы и отладочный код.
- В итоговом сообщении указывай, что изменено, что проверено и что проверить не удалось.
- Пока проект не содержит кода и настроенных инструментов, не придумывай команды запуска или проверки.
